# 即将执行（Upcoming Preheat）· 设计记录

> 记录于 2026-09-15，由 Operator 提出：「希望有一个地方能看到下一批计划，
> 例如 2026/09/15 05:30 批次下拉展开显示 账号1: 计划时间」。
> 本文是设计的持久记录，**不构成实施授权**；实施与发版另行确认。

**Surface:** 单页嵌入式面板（`web/panel.html`，源码分布在 `web/modules/*.js`）。

**Mode:** Operate。访问者要完成的任务是判断「自动预热是否还活着、下一次在什么
时候、届时会不会被跳过」。可扫描性与一致性优先于表现力。

**Scope discipline:** 在既有实现上做增量，不替换视觉世界。蓝白运维控制台的
identity、中文优先的文案、以及所有 host API 契约保持不变。

## 立项理由

v0.0.21 及更早版本中，一次重启会让整个计划视野失效（见
`docs/releases/v0.0.22.md`）。该缺陷在 Operator 的部署上持续了约一周，期间
**面板上没有任何一处能看出异常**：

- 检测历史是空的——但空历史也可能只是「还没到时间」，无法区分。
- 模拟器一切正常——因为它算的是假设，不读真实的已挂定时器。
- 摘要条、账号表、额度快照全部正常。

面板当时只有「过去」与「假设」两种视图，唯独没有「接下来真的会发生什么」。
因此本组件按**可观测性**设计，而非按日程表设计：它的首要职责是让静默失效在屏幕
上显形，展示排期是其次。

## 数据现状

- `/status` 已返回 `next_runs: {occurrenceID: time}`
  （`internal/management/types.go:74`，源自 `domain.StatusView.NextRuns`）。
- 面板当前**完全没有使用**它。唯一的引用在 `web/modules/accounts.js:210`，
  属于未接入的遗留模块。
- occurrence ID 形如 `2026-09-15/p1/acct-58baed010f75dd6e`，编码了日期、时段
  序号与账号。

## 设计

### 一、两层结构

**第一层 · 摘要条旁一行**，回答「系统还活着吗」：

```
下一次预热 · 今天 10:31 · 3 个账号
```

首屏可见、无需展开。与既有的 `额度快照 · 12 分钟前`（F3）属同一族全局健康信号，
并排放置。

**第二层 · `即将执行` 面板，置于 `检测历史` 正上方**，使用 Operator 描述的批次
下拉。两者构成一对：过去的批次与未来的批次，复用同一套 `<details>` 交互与视觉
语言，不引入新交互模式。

命名取 **即将执行**。不取「预热计划」——与配置区的计划/排期措辞冲突。

### 二、按预热窗口分组，不按分钟分组

账号在窗口内按设计错峰（Operator 的三个凭证为 10:31:40 / 10:35:00 / 10:38:20），
它们本就是一批。这也与检测历史「同一计划时段的错峰预热归为一批」一致。

批次头：

```
今天 10:30–10:40 · 计划时段 2 · 3 个账号 · 2 小时后
```

| 字段 | 作用 |
| --- | --- |
| 日期 | 仅跨天时出现：今天 / 明天 / 09-17 |
| 窗口区间 | 与模拟器、历史的时段口径一致 |
| 计划时段 N | 与检测历史批次头对齐 |
| 账号数 | 批次规模 |
| 相对时间 | 放在末尾但语义最重——「还有多久」比「几点」更接近真实问题 |

### 三、展开后的账号行

```
b***@example.com        10:31:40
r***@example.com        10:35:00
n***@example.com        10:38:20   Guardrail Hold · 届时将跳过
```

- **遮罩身份必须跟随现有的「显示身份」开关**，否则会出现两套遮罩逻辑。
- 正常行不加「已就绪」之类徽章。三行三个绿标是纯噪声；异常才值得占视觉预算。

### 四、明确不做的事

- **不预测额度判断结果。** 「额度充足所以预计跳过」依赖执行那一刻的额度；用数
  小时前的快照推断，正是 F3 指出的「数字看起来同样权威，不管它是不是当前的」。
  只显示此刻已知的确定性阻塞：账号已停用、Guardrail Hold 生效中——这两个是持久
  状态，不是预测。
- **不做跳秒倒计时。** 面板刻意不轮询（ADR-0011）；实时跳动的倒计时会暗示一种
  它并不具备的实时性。渲染时计算一次相对时间即可。
- **不默认铺开 8 天。** 视野内约 24 个批次且高度重复。默认只显示「今天剩余 +
  明天」，其余收进「查看完整计划视野（8 天）」折叠。

### 五、空状态是主要功能，不是兜底

| 情况 | 呈现 |
| --- | --- |
| 计划未启用 | 中性，指向首次配置清单（复用 F5 措辞） |
| **已启用但无任何待执行** | **警示态**。文案直述：`计划已启用，但没有任何待执行的预热` |
| 下一次预热在 24 小时以后 | 琥珀色提示 |
| 存储错误（`store_error_code`） | 明说读不到状态，不得呈现为「暂无计划」 |

第 2、3 条是本组件的核心价值。v0.0.22 修复前，Operator 的部署会命中第 3 条
（最近的定时器在 7 天后）；若视野被完全清空则命中第 2 条。

## 需要的后端改动

occurrence ID 虽然编码了日期/时段/账号，**前端不得解析它**——那会把 UI 焊死在
ID 格式上，而该格式已因 v0.0.16 的批次重编号改动过一次。

新增 `GET /upcoming`，由服务端完成分组：

```json
[{ "local_date": "2026-09-15", "period_index": 1,
   "window_start": "...", "window_end": "...",
   "occurrences": [
     { "account_key": "...", "masked_identity": "...",
       "planned_at": "...", "blocked_reason": "guardrail_hold" }]}]
```

遮罩身份与 guardrail 状态本就在服务端，放在这里最省事，同时让 occurrence ID
保持不透明。另在 `/status` 增加标量 `next_run_at`，供第一层那行使用，避免为一行
文字拉取整个列表。

## 必须一并处理的冲突

模拟器的 `预热时段概览` 副标题为 **「来自服务端调度器」**
（`web/modules/timeline.js:232`）。该措辞现在具有误导性：它是用**草稿配置**推算
**某一天**的假设结果，并非真正挂上定时器的排期。两块外观相近的区域并存而措辞不
作区分时，Operator 会把模拟器的概览当作「排期已生效」的证据。

方向：模拟器该副标题改为明确的模拟口径（如「按当前草稿参数推算」），把「这是真
实排期」这层权威**唯一地**留给新面板。

## 实施顺序

1. 后端：`GET /upcoming` + `/status` 的 `next_run_at`。
2. 前端第一层：摘要条旁的一行 + 四种状态。
3. 前端第二层：`即将执行` 面板与批次下拉。
4. 模拟器副标题措辞修正。

1 与 2 已能独立交付本组件的全部可观测性价值；3 是排期展示，4 是防误读。

## 实施记录 · 第 1、2 步（2026-09-15）

已实现后端与第一层，第三、四步未动。

### 与本文原设计的两处偏离

1. **`masked_identity` 不由 `/upcoming` 返回。** 原文写「遮罩身份与 guardrail
   状态本就在服务端，放在这里最省事」——对 guardrail 成立（在 runtime state
   里，零额外调用），对遮罩身份不成立：它需要一次账号发现（host 调用），而面板
   每次载入本就已经取过账号列表。多这一次发现与 v0.0.19「削减重复账号发现」的
   方向相悖。改为只返回 `account_key`，由前端与已有账号列表做一次 map join。
   真正要避免的耦合是「前端解析不透明的 occurrence ID」，这一点仍然守住了。

2. **`next_run_at` 放在 `/upcoming` 而非 `/status`。** 原文的理由是「避免为一行
   文字拉取整个列表」，但视野内批次很少、载荷只有几 KB，且面板本就并行拉取多个
   端点。为同一事实开两个来源不值得，因此单一来源为 `/upcoming`，`/status` 不变。

### 已落地

- `domain.UpcomingView` / `UpcomingBatch` / `UpcomingOccurrence`
  （`internal/domain/upcoming.go`），`blocked_reason` 目前仅有 `guardrail_hold`。
- `Runtime.Upcoming()`（`internal/app/upcoming.go`）：以 **NextRuns 为「已挂定时器」
  的权威**，而非 occurrence 表——没有 NextRuns 条目的槽位不会触发，而这正是重启
  缺陷能够静默破坏的地方。仅纳入 `planned` 状态；`failed` 上的 NextRuns 条目是
  补偿重试，属于另一个概念。
- `GET /upcoming` 管理端点与路由注册。
- 第一层：摘要条首位的 `#next-run`，五种状态
  off / ready / distant / alarm / error，由纯函数 `describeNextRun()` 决定
  （`web/modules/dashboard.js`）。

### 已知口径

时间按**浏览器本地时区**格式化，与面板既有的 `formatDate` 一致，而非按
`config.timezone`。本次不引入第二套时区策略；如需改为按配置时区显示，应作为一次
独立的全面板改动。

### 验证

- Go：4 个 `Upcoming` 回归（分组与错峰顺序、只纳入已挂定时器的 planned 槽位、
  guardrail 标注且不预测额度、空/未启用/不可读三者可区分）。前两个已用变异测试
  反证——改成遍历 occurrence 表或去掉 guardrail 判断后确实失败。
- 前端：`web/tests/upcoming.test.mjs` 6 项（含「7 天后」那条真实故障形态）。
- 浏览器：`audit-next-run`（1440）与 `audit-next-run-narrow`（375），后者额外断言
  最长的告警文案不会撑破页面。
- 全量：`gofmt`/`go vet`/`go build`/`go test`/`go test -race` 干净；
  `node --test` 78 通过 0 失败。
