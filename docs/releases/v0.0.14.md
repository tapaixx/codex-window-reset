# Codex Window Reset v0.0.14

修复 v0.0.13 的发布阻塞：同步模拟器浏览器验收和静态测试数据中的第三次预热（16:30），并断言三个执行时间 06:30、11:30、16:30。保留原有 A/B 覆盖区间、移动端、明暗主题检查，不删除或跳过发布门禁。

## v0.0.13 发布失败复盘

- 失败提交：`084c367`；[Release 日志](https://github.com/tapaixx/codex-window-reset/actions/runs/34758036808)、[CI 日志](https://github.com/tapaixx/codex-window-reset/actions/runs/34758036817)。
- 两个架构均在 `web/tests/browser.test.mjs` 的模拟器场景断言失败：`actual: 3, expected: 2`。Go 测试已通过；Release 的验证任务失败使打包发布任务无法执行。
- 直接原因：调度器增加了最后工作时段对应的预热后，Go 真实响应包含三个标记，浏览器测试仍要求两个。
- 漏检原因：源码浏览器测试使用 `web/tests/simulation-fixture.mjs`，其静态数据同样停留在两个标记；CI 使用 `TestExportEmbeddedPanelForBrowser` 导出的实际页面和 Go 模拟结果。仅测静态数据无法发现两者漂移。之前将未查明的浏览器测试失败称为环境问题，没有依据。

## 防止复发

1. 修改计划、窗口边界或时间轴时，同时核对 Go 计划测试、静态模拟数据和真实嵌入页面的浏览器验收。用手算时间点作断言，不能只改成接受任意标记数量。
2. 对这类变更，至少运行同一失败用例的源码页面和真实嵌入页面两种模式。用 `CWR_BROWSER_FIXTURE_DIR` 导出后，将 `BROWSER_PANEL_FILE`、`BROWSER_SIMULATION_FILE`、`BROWSER_EXPECTED_VERSION` 传给浏览器测试；筛选命令为 `node --test --test-name-pattern='^simulator renders different' web/tests/browser.test.mjs`。完整发布门禁仍由 `scripts/verify-panel.sh` 执行。
3. 浏览器失败必须保留并读取实际断言和退出码。未定位时记录“未验证”，不能推断为环境问题或声称已经通过。
4. 本地打包、标签推送、Actions 成功、Release 附件就绪是不同状态；只有确认 Release 和双架构附件存在，才报告发版完成。
5. 已推送的失败标签保留不动；修复使用新的补丁版本，避免覆盖版本历史。

此版本不清空配置或检测数据，也不改变 v0.0.13 的生产逻辑。
