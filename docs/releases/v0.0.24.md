# Codex Window Reset v0.0.24

修复热升级导致的**同一账号被预热两次**，并补回上游对「现在能否使用」的判决。

## 被替换的插件实例不再执行任务

主机热加载新插件构建但不卸载旧实例时，同一个数据目录上会同时存在两个调度器。
`handleOccurrence` 的槽位抢占是一次读-改-写，只受**各自实例**的互斥锁保护，跨实例
并不原子，因此两个实例可以把同一个槽位都从 `planned` 翻成 `running`。

在报告问题的部署上，容器自前一天起未重启，而 v0.0.23 在批次开始前 27 分钟被装入：

```
自动预热 · 计划时段 3 · 3 个账号 · 4 次操作
  a***@qq.com     15:31:40 · sufficient_window   ← 旧实例（v0.0.22 及更早）
  w***@gmail.com  15:35:00 · window_active       ← 新实例（v0.0.23）
  c***@gmail.com  15:38:20 · sufficient_window   ← 旧实例
  c***@gmail.com  15:38:20 · window_active       ← 新实例
```

一个批次里出现两个版本的判定值，只可能是两份代码同时在跑。未重复的两个账号各自
只执行一次，是因为其中一个实例赢下了抢占竞争——这也解释了为什么同一批次会混用
两个版本的判定逻辑。

- 运行时状态新增调度所有者，**启动时写入、之后只读**，因此两个实例无需共享锁即可
  对所有者达成一致；**后启动的赢**，新构建接管而不是与前任竞争。
- 被接管的实例继续提供读接口，但永不发出上游请求。
- 它仍会挂定时器，所以会在面板首行明示「另一个插件实例已接管调度，本实例不会
  执行」——定时器响了却不做事，否则和正常调度毫无区别。

**升级后请重启一次 CLIProxyAPI**：本修复能防止再次发生，但当前进程里已经存在的
旧实例只能靠重启清除。同时建议清掉 `plugins/linux/<arch>/` 下的历史 `.so`，只保留
最新版本。

## 保留上游的可用性判决

真实的 `wham/usage` 响应在百分比之外还带着上游自己的执法判决：

```json
"rate_limit": { "allowed": true, "limit_reached": false, "primary_window": { "used_percent": 100, ... } },
"rate_limit_reached_type": null,
"model_usage": { "gpt-6-astra": { "available": true, "available_at": null } }
```

解析器只在 `used_percent` **缺失**时才参考 `limit_reached`，而该字段始终存在，因此
上述判决全部被丢弃，快照完全靠百分比推断可用性。

用量百分比和执法判决是**两个不同的事实**，且可以互相矛盾：一个窗口可以显示为已经
用尽，而上游仍然允许发请求。仅凭百分比推断会把尚可使用的账号报成没有额度，而且
**这种误报从面板上无法证伪**——每次刷新都返回同一个百分比，因为它是准确的，只是
回答了另一个问题。

- 快照现在保留 `limit_reached`、`rate_limit_reached_type`，以及不可用模型中最早的
  恢复时间。
- 窗口单元格在两者矛盾时直接说明：余量为 0 但仍被允许时显示「上游报告仍可请求」；
  确实被限流时显示「上游已限流（类型），HH:MM 恢复」。

这是为一个**尚未复现**的报告（凭证显示无额度但实际可用）做的观测铺垫，**不是已确认
的诊断**。它消除了让该症状无法检验的那层推断：下次出现时，面板会直接说明究竟是
上游仍允许、上游确实限流，还是上游返回了陈旧数据。

## 验证

- 双实例回归在同一个状态仓库上并行启动两个调度器，断言被接管的实例执行 0 次、
  当前实例执行 1 次；已用变异测试反证——去掉所有者判断后该回归立即失败。
- 可用性回归直接使用抓取到的真实上游响应体，把 `used_percent` 改为 100 而保留
  `limit_reached: false`，断言两个事实都被保留。
- 浏览器回归覆盖两个方向：仍可请求、以及带类型与恢复时间的已限流。
- `gofmt` / `go vet` / `go build` / `go test` / `go test -race` 全部干净；
  `node --test` 110 通过 0 失败。
