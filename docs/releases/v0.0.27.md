# Codex Window Reset v0.0.27

修复面板在升级宿主管理面板后整体不可用的问题:所有请求返回 401,页面一片空白,
并报告「CLIProxyAPI 管理密钥无效或已变更」——而密钥既没有失效也没有变更。

## 读取管理面板的 v2 密钥信封

面板从 localStorage 取宿主管理密钥,而管理面板把该值**混淆后**存放,并在值的前缀
写明方案版本。此前只处理了 `enc::v1::`,其余版本会**原样返回**,于是面板发出了
`Authorization: Bearer enc::v2::...`,宿主自然拒绝,每一个请求都变成 401。

由于面板的全部数据都依赖这些请求,表现是配置、账号、历史、排期同时消失,看起来像
数据丢失;而实际的排期配置一直完好。

这套混淆机制源自**官方管理面板**(router-for-me/Cli-Proxy-API-Management-Center),
它目前仍写 v1;**cpa-manager-plus 分叉后新增了 v2**。插件面板会被嵌入部署方实际
使用的那一个,因此两种都必须能读:

```
v1:  ${namespace}|${location.host}|${navigator.userAgent}
v2:  ${namespace}|v2|${location.host}
```

两者都从命名空间与页面 host 派生密钥,v1 额外混入 User-Agent,v2 改为版本标记。
现在均可解码。

## 无法解码的信封不再冒充密钥

遇到本插件不认识的版本时:

- **不再**把信封原样作为 Bearer 令牌发出——那正是这次产生误导性 401 的原因。
- 401 的提示改为说明**存储格式**并给出版本号,例如「宿主管理面板的密钥存储格式
  (v3)本插件无法读取,请升级插件」,而不是指责一个完好无损的密钥。

## 关于后续版本的说明

**本插件无法预先兼容未来的 v3、v4。** 每个版本的密钥派生规则是任意的,不是同一
格式的不同参数,不知道规则就无法解密。两条可以摆脱该依赖的路径都已确认不可行:
两个管理面板均未提供 `postMessage` 凭据握手,而 CPA 的管理中间件只接受
`Authorization` 或 `X-Management-Key` 请求头,没有任何 cookie/会话路径。

因此本版的目标不是"永久兼容",而是**让下一次不兼容能被一眼看出原因**,而不是表现
为配置消失加上一句错误的密钥指控。

## 验证

- 互通验证不依赖对算法的复述:从 cpa-manager-plus 的二进制与官方面板的
  `management.html` 中**原样提取各自的混淆函数**并执行,用它们自己的代码生成信封,
  再交由本插件解码。两者均完全匹配,且分别使用了不同的载荷结构
  (`{managementKey}` 与 `{state:{managementKey}}`)。
- 单元测试覆盖:v2 可解、v1 仍可解、明文仍可用、无法识别的信封绝不外发、401 文案
  按情况切换。已用变异测试反证——移除 v2 支持后相关用例立即失败。
- `gofmt` / `go vet` / `go build` / `go test` / `go test -race` 全部干净;
  `node --test` 116 通过 0 失败。

## 升级后

安装本版并重启 CPA 后,**请硬刷新面板**(Ctrl+Shift+R),确保浏览器加载的不是缓存
的旧脚本。
