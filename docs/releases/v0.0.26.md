# Codex Window Reset v0.0.26

两处报告层修复,都来自同一个真实批次。本版不改变任何调度或判定行为。

## 被跳过的槽位不再显示为「已停用」

`disabled` 这个请求结果的含义是**没有发送请求**,而不是账号被停用。账号表的
`上次检测` 列把它映射成了「已停用」并套用失败样式,于是一个完全健康的凭证——它那
一轮只是因为窗口已在运行而被正确跳过——挂上了红色的停用标记。

真实记录:

```
a***@qq.com  outcome=disabled  window=not_observed  decision=window_active
```

检测历史面板在 v0.0.24 已经改为显示「未发送请求」并说明判定原因,但账号表这一列
当时**没有一并修改**。现在两处一致:该列显示中性的「未发送」,下方写明判定原因。

## 窗口验证等待上游反映出新窗口

后置额度读取紧跟探测返回,而上游的 usage 接口不会那么快更新。同一批次里两次成功的
预热——事后从窗口自身的起始时间可以确认——都被记成了 `unchanged`:

| 账号 | 探测时刻 | 窗口实际开始于 | 当时记录 |
| --- | --- | --- | --- |
| w***@gmail.com | 05:31:40 | **05:31:43** | `unchanged` |
| c***@gmail.com | 05:38:20 | **05:38:27** | `unchanged` |

也就是说,一次完全做到了本职工作的预热被报告成「没能开窗」。

后置读取现在在确认失败时重试两次(2 秒、4 秒),窗口一出现即停止。它**只走这条
假阴性路径**:

- 首次读取已经看到窗口 → 立即返回
- 请求本身未成功 → 立即返回
- 请求前账号就已在窗口内 → 立即返回
- 刷新报错或超时 → 立即返回,因为重复一个失败的读取无助于结果,而预热不能被它拖住

因此一次正常的预热不会产生任何额外的上游调用。

## 验证

- 新增回归:请求前空闲、请求后首次读取仍为空闲、随后窗口出现,断言最终判定为
  `verified_started`。已用变异测试反证——移除重试循环后该测试立即失败并给出
  `unchanged`。
- 浏览器回归新增断言:被跳过的槽位在账号表中显示为「未发送」,不带失败样式,并在
  详情里给出判定原因。
- `gofmt` / `go vet` / `go build` / `go test` / `go test -race` 全部干净;
  `node --test` 111 通过 0 失败。

## 关于 v0.0.25 的实地结果

v0.0.25 修复用量单位解析之后,预热首次真正开出了窗口(上表两条)。在此之前,
`used_percent: 1` 被读成用满 100%,长窗口上的同一误读还会触发 Guardrail Hold。
本版不改变该行为,只让记录如实反映它。
