# Codex Window Reset v0.0.23

修复一个使自动预热**即使按时触发也永远不会真正执行**的判定缺陷，并补上面板此前
完全缺失的「接下来会发生什么」视图。建议所有使用自动预热的部署升级。

## 空闲账号被误判为「窗口已满」，预热因此一次都不会发生

v0.0.22 修好了定时器之后，调度按计划准时触发了，但三个账号全部被跳过，判定为
`sufficient_window`。

根因：**上游没有「当前没有窗口在跑」这个表示。** 账号空闲时它返回的是一个尚未
开始的完整窗口——消耗 0%，重置时间正好一个完整周期之后。实测同一账号相隔 67
分钟的两次读取：

| 读取时刻 (UTC) | 短窗口 reset_at | 差值 | 余量 |
| --- | --- | --- | --- |
| 04:12:54 | 09:12:54 | +300.0 分钟 | 100% |
| 05:19:28 | 10:19:29 | +300.0 分钟 | 100% |

`reset_at` 跟着读取时间滑动，永远是「此刻 + 5 小时」。旧判定把它当成「有一个开着
的窗口，余量 100%，还有 5 小时才重置」，于是两个阈值永远同时满足，永远跳过。

而账号空闲恰恰是**唯一**能靠一个请求开出新窗口的时刻。这个判断把预热锁死在了它
唯一有用的场景上。

- 新增 `UsageWindow.ActiveAt()`：真正运行中的窗口是过去某刻开始的，因此
  `reset_at − captured_at` **严格小于**一个完整周期；占位值恰好等于一个周期。
- 30 秒时钟偏差容差内两者无法区分，判定**倒向预热**——多发一次请求代价是一个
  便宜的调用，少发一次就是本缺陷本身。

## 窗口正在运行时一律跳过，不再看额度阈值

一个预热请求只可能在没有窗口运行时开窗。发进一个正在运行的窗口里既开不出第二个
窗口，又要消耗额度——而旧规则恰好在最不该发的时候放行：短窗口余量低于
`remaining_quota_floor_percent` 或距重置短于 `remaining_window_floor_minutes` 时
会落到 `proceed`，把所剩不多的额度花掉。

现在每个凭证**独立**按两步判定：

```
① 该凭证自己的长窗口余量 > long_window_floor_percent？  否 → Guardrail Hold，跳过
② 该凭证自己有窗口在跑吗？                              是 → window_active，跳过
                                                        否 → 预热
```

- 判定值由 `sufficient_window` 改名为 `window_active`，旧名字描述的是一个不再做的
  额度判断；已写入的历史记录仍可正常显示。
- `remaining_quota_floor_percent` 与 `remaining_window_floor_minutes` 不再参与任何
  判定，**已从配置表单移除**。字段本身仍被接收、校验与存储，保存时原样带回，
  不会重写你已保存的值。`long_window_floor_percent` 是唯一仍在起作用的阈值。

## 窗口验证不再把「什么都没开」记成「已开窗」

同一个占位值缺陷的镜像版本：验证原本比较请求前后的 `reset_at`，而空闲账号的这个
值本来就在滑动，**只要时间流逝就会「验证通过」**。现在直接判断请求之后是否真的
有窗口在运行：之前没在跑、之后也没在跑 → `unchanged`（请求没能开窗）。

## 检测历史说明跳过原因

一次按设计跳过的批次此前渲染为
`请求：disabled · 窗口：not_observed · HTTP -- · 0 ms`，唯一能解释原因的
`decision` 字段根本没有显示，读起来和失败一模一样。

`disabled` 在这里不是「已停用」，而是「没发请求」。现在：

```
自动预热 · 计划时段 2 · 3 个账号 · 3 次操作 · 全部跳过，未发送请求
  c***@gmail.com · 10:31:40 · 自动预热 · 未发送请求 · 窗口已在运行，无法再开新窗口
```

没发出的请求不再显示请求结果、窗口结果、HTTP 与耗时——那些是给一个非事件编造的
读数。批次头明示跳过次数。Guardrail Hold 的 `decision` 与 `error_code` 值相同，
只说一次。未知的新判定值原样显示而非消失。

## 新增「即将执行」与「下一次预热」

面板此前只有「过去」（检测历史）与「假设」（模拟器），没有「接下来真的会发生
什么」。v0.0.22 的重启缺陷之所以能静默运行一周，正是因为这个缺口。

- 摘要条首位新增一行，五种状态：计划未启用 / 已挂定时器 / **下一次超过 24 小时
  之后** / **已启用但没有任何待执行** / 读取状态失败。后两种是警示态——停摆的
  调度器留下的正是这两种形态。
- 新增 `即将执行` 面板（位于检测历史上方）与 `GET /upcoming`：按预热窗口分组，
  展开显示每个账号的错峰执行时刻；仅对**此刻已为真**的条件标注阻塞
  （Guardrail Hold / 已停用 / 不可用），不预测额度判定。默认只显示今天与明天，
  折叠时明示还有多少批。
- **以 NextRuns 为「已挂定时器」的权威**，而非 occurrence 表：没有定时器的槽位
  不会触发，而这正是重启缺陷能静默破坏的地方。
- 模拟器「预热时段概览」副标题由「来自服务端调度器」改为「按当前草稿参数推算」，
  它是草稿推算而非已生效排期。

## 账号表修正

- **套餐类型**此前显示 `oauth`。主机的 `account_type` 是**凭证类型**，套餐在
  OAuth `id_token.plan_type` 里。Go 与前端都改读该字段，并把 `account_type` 从
  兜底链中移除——它永远不可能是套餐。已知档次做大小写映射，未知值原样透传。
- **状态**此前恒为「警告」且不说原因。面板刻意不轮询，「还没有额度快照」是打开
  面板后的正常状态，却被算进了和真实故障同一档。现在：无快照是中性的「未刷新」；
  真实问题各自报出条件（不可用 / 刷新失败 / 已停用）；每个徽章都带说明。
- **快照年龄不再算故障**。每次预热都会在判定前立刻刷新额度，年龄从不阻塞预热；
  五分钟的过期边界是给判定用的，不是给这一列用的。刷新失败时时间列明示
  「刷新失败，保留上次快照」。`snapshotStaleAfter` 常量未改动。
- **重置额度**一行列出全部到期时间（最早在前），hover 显示完整时间戳与总数。

## 验证

- 复现用的 fixture 直接照搬真实上游 payload 形状；判定修复经过**反证**：移除
  `ActiveAt` 判断后测试立即失败并给出与线上一致的 `sufficient_window`。
- 新增覆盖：空闲账号必须预热、运行中窗口无论余量一律跳过、**短窗口只剩 5% 且
  20 分钟后重置仍然跳过**（旧逻辑在此放行）、滑动占位不算开窗、失败请求永不算
  开窗、退休字段保存时不被重写。
- `gofmt` / `go vet` / `go build` / `go test` / `go test -race` 全部干净；
  `node --test` 105 通过 0 失败。

## 升级后预期

重载插件后，上班前的预热轮次应当真正发送请求并在检测历史中出现
`请求：成功 · 窗口：已开窗`。落在活动窗口中间的轮次仍会显示
`未发送请求 · 窗口已在运行，无法再开新窗口`——那是正确行为，此时发请求开不出新
窗口。无需删除任何配置或历史文件。
